# INC-0003 — Tomcat Upstream Service Outage

## Incident Information
- Environment: VMware Ubuntu Server 24.04 Homelab
- Hostname: dc-labsrv01
- Date: 2026-11-01 (UTC)
- Status: Resolved
- Type: Controlled outage simulation
- Impact: Tomcat application unavailable through Nginx reverse proxy
- Scope: Local homelab only

## System Architecture
- Nginx: Port 80 (static website)
- Nginx Reverse Proxy: Port 8081
- Apache Tomcat: Port 8080
- Upstream: http://127.0.0.1:8080/

## Incident Timeline (UTC)
- Before incident: Reverse proxy returned HTTP 200
- Tomcat service intentionally stopped
- 20:36:50 — HTTP 502 Bad Gateway observed
- 20:36:50 — Nginx error log recorded upstream connection refusal
- Tomcat service restarted
- 20:44:58 — HTTP 200 confirmed through reverse proxy

## Symptoms
- GET /tomcat/ returned HTTP 502 Bad Gateway
- Nginx continued responding to HTTP requests
- Tomcat application content was unavailable

## Investigation
Command:
curl -i --max-time 5 http://127.0.0.1:8081/tomcat/

Observed:
HTTP/1.1 502 Bad Gateway

Nginx error log:
connect() failed (111: Connection refused) while connecting to upstream

Upstream:
http://127.0.0.1:8080/

## Root Cause
Apache Tomcat was intentionally stopped using systemctl.
Nginx could not establish a TCP connection to the Tomcat upstream on port 8080.

## Resolution
Command:
sudo systemctl start tomcat10

## Recovery Verification
Command:
curl -i --max-time 5 http://127.0.0.1:8081/tomcat/

Results:
- HTTP 200
- Server: nginx/1.24.0 (Ubuntu)
- Apache Tomcat default HTML returned
- Content-Length: 1905 bytes

## Lessons Learned
- HTTP 502 can indicate an upstream application failure.
- A functioning reverse proxy does not guarantee backend availability.
- Nginx error logs help isolate upstream connection problems.
- Restore the affected service rather than restarting unrelated services.
- Verify recovery using an end-to-end HTTP request.

## Limitations
- This was a controlled homelab simulation, not a production incident.
- External client access was not tested during recovery.
- No monitoring alerts or automatic failover were configured.
