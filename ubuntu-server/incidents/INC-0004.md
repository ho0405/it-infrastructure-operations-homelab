# INC-0004 — PostgreSQL Database Connection Failure

## Incident Classification
- Type: Controlled database availability incident
- Environment: Personal Ubuntu Server 24.04 VMware homelab
- Service: PostgreSQL 16.15, cluster 16/main
- Impact: Local application database connections unavailable during shutdown
- Production impact: None; this was an intentional lab simulation

## Incident Timeline (UTC, 2026-11-01)
- 21:25:59 — PostgreSQL started and became ready for connections.
- 21:32:55 — PostgreSQL received a fast shutdown request.
- 21:32:55 — Shutdown checkpoint completed and database system shut down.
- Following shutdown — pg_lsclusters reported down.
- Following shutdown — lab_app connection to 127.0.0.1:5432 failed with Connection refused.
- Following shutdown — ss showed no TCP listener on port 5432.
- Recovery — PostgreSQL cluster restarted and reported online.
- 21:37:21 — Authenticated lab_app SQL query succeeded after recovery.

## Detection and Diagnostic Evidence
Cluster status: 16 main 5432 down postgres.
Client error: connection to server at 127.0.0.1, port 5432 failed: Connection refused.
Socket inspection: no LISTEN entry for TCP port 5432.
PostgreSQL log: received fast shutdown request.
PostgreSQL log: database system is shut down.

## Root Cause Analysis
The operator deliberately stopped PostgreSQL cluster 16/main for a controlled incident exercise. This removed the TCP listener on port 5432. Client TCP connection attempts were therefore refused before PostgreSQL authentication could occur.
The observed shutdown log is consistent with the intentional stop. No independent crash or authentication failure was established.

## Recovery Procedure
1. Start the PostgreSQL cluster using pg_ctlcluster.
2. Verify pg_lsclusters reports online.
3. Connect to 127.0.0.1:5432 using lab_app and password authentication.
4. Execute SQL to verify the application identity, database, port, and server timestamp.

## Recovery Evidence
- Cluster: 16/main online on port 5432.
- current_user: lab_app.
- current_database: lab_db.
- inet_server_port: 5432.
- Query timestamp: 2026-11-01 21:37:21 UTC.
- Result: one SQL row returned successfully.

## Corrective and Preventive Actions
- Restore the database service and verify an actual SQL query.
- Monitor cluster health and TCP listener availability.
- Document authorized maintenance shutdowns to avoid confusion with unexpected outages.
- Consider service monitoring and alerting in a future lab.
- Implement and test backup/restore procedures in a future chapter.

## Lessons Learned
- Connection refused is a TCP connectivity symptom, not a password error.
- Service status alone is insufficient to prove application recovery.
- Logs, process state, socket inspection, and SQL tests provide complementary evidence.
- This incident was simulated; findings must not be represented as professional production incident experience.
