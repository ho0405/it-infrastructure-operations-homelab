# INC-0005 — Accidental PostgreSQL Data Deletion

> Controlled homelab incident simulation. Not a production outage.

## Incident Summary
- Date: November 1, 2026
- Host: dc-labsrv01
- Database: lab_db_recovery (isolated recovery test)
- Affected table: public.lab_assets
- Incident type: Accidental data deletion
- Status: Recovered and validated

## Impact
- Five fictional infrastructure asset records were deleted from the recovery database.
- The affected table went from five records to zero records.
- The original lab_db database was not modified.
- No production systems or customer data were affected.

## Root Cause
A DELETE statement was deliberately executed without a WHERE clause as part of the incident simulation.
The statement completed successfully and removed all five rows.
Because it was executed without an explicit transaction block, the completed statement was committed and could not be reversed by a subsequent ROLLBACK.

## Detection and Diagnosis
Command: sudo -u postgres psql -d lab_db_recovery -c "DELETE FROM lab_assets;"
Observed output: DELETE 5
Command: sudo -u postgres psql -d lab_db_recovery -c "SELECT COUNT(*) AS remaining_records FROM lab_assets;"
Observed result: remaining_records = 0

## Recovery Procedure
Backup source: /tmp/ch06_lab_db_backup.dump
Backup format: PostgreSQL custom archive, created using pg_dump -Fc.
Command: sudo -u postgres pg_restore --verbose --exit-on-error --data-only -d lab_db_recovery /tmp/ch06_lab_db_backup.dump
Observed result: Table data processed and sequence state restored without reported errors.

## Recovery Validation

- All five deleted records were recovered.
- Original asset IDs, hostnames, types, and statuses matched.
- Source database: lab_db|5|1|5.
- Recovery database: lab_db_recovery|5|1|5.
- Sequence: last_value=5, is_called=true.
- Result: Recovery objective achieved in the isolated lab.

## Recovery Limitations

- RPO and RTO were not defined or measured.
- Recovery used a logical backup, not point-in-time recovery.
- The backup was stored in /tmp on the same VM.
- No production systems or customer data were involved.

## Prevention and Improvements

1. Review WHERE clauses before executing DELETE or UPDATE.
2. Use explicit transactions for high-risk changes.
3. Apply least-privilege database permissions.
4. Automate backups and monitor failures.
5. Store encrypted backups off-host.
6. Test restores regularly and verify data integrity.
7. Define measurable RPO and RTO targets.

## Lessons Learned

A successful backup command does not guarantee recoverability.
An isolated restore test, SQL verification, and sequence validation
provide stronger evidence of recovery readiness.
