# INC-0012 — Apache Remote Access Failure Caused by firewalld

## Environment

- OS: Rocky Linux 10.2 ARM64
- Hostname: dc-lab-rhel01
- Platform: VMware Fusion on Apple Silicon
- Network: VMware NAT
- Server IP: 192.168.24.130
- Web Server: Apache HTTP Server 2.4.63
- Firewall: firewalld
- Environment Type: Controlled homelab

## Incident Summary

Apache was running and responding successfully to local HTTP requests, but a remote client could not establish a connection to TCP port 80.

The incident was caused by an active firewalld zone that did not permit the HTTP service.

## Initial Symptoms

Local HTTP test: 200 OK

Remote Mac HTTP test: Connection failed

SSH remote access: Available

## Root Cause

The public firewalld zone allowed SSH but did not include the HTTP service.

The web server was operational, but the host firewall blocked incoming HTTP traffic.

## Investigation

First, the Apache service was confirmed to be running.

A local HTTP request returned 200 OK, indicating that the web server was responding successfully.

The same application was then tested from the Mac host.

The remote connection failed on TCP port 80.

The active firewall configuration was inspected using:

```bash
sudo firewall-cmd --state
sudo firewall-cmd --list-all
```

The active zone was public, associated with interface enp2s0.

Initially allowed services:

```text
cockpit dhcpv6-client ssh
```

The HTTP service was not allowed.

## Diagnosis

The difference between successful local access and failed remote access indicated a network access problem rather than an Apache application failure.

The firewalld configuration confirmed that incoming HTTP traffic was not permitted.

## Resolution

The HTTP service was first allowed in the active public zone.

```bash
sudo firewall-cmd --zone=public --add-service=http
```

The command returned success.

After this change, the Mac host successfully accessed Apache and received HTTP 200 OK.

The active and permanent configurations were compared.

Runtime HTTP access: yes
Permanent HTTP access: no

To ensure the rule would survive a firewall reload, the permanent configuration was updated.

```bash
sudo firewall-cmd --permanent --zone=public --add-service=http
sudo firewall-cmd --permanent --zone=public --query-service=http
```

The permanent rule verification returned yes.

The firewall configuration was then reloaded.

```bash
sudo firewall-cmd --reload
```

The reload returned success.

## Post-Change Validation

The active public zone services were checked.

```bash
sudo firewall-cmd --zone=public --list-services
```

Observed services:

```text
cockpit dhcpv6-client http ssh
```

The Mac host was able to connect to Apache after the reload.

Observed HTTP response: HTTP/1.1 200 OK

SSH connectivity remained available.

## Configuration Backup

The permanent public zone configuration was backed up before further rollback testing.

Backup directory:

~/data-centre-infrastructure-lab/backups/ch13/

Source configuration:

/etc/firewalld/zones/public.xml

The backup was verified using:

```bash
sudo diff -s /etc/firewalld/zones/public.xml ~/data-centre-infrastructure-lab/backups/ch13/public.xml.backup
```

Observed result: Files are identical.

## Lessons Learned

1. A running web server does not guarantee remote availability.
2. Compare local and remote connectivity to narrow down the fault domain.
3. Check the active firewall zone before changing rules.
4. Understand the difference between runtime and permanent configurations.
5. Verify application connectivity after a firewall reload.
6. Preserve a verified configuration backup before rollback testing.

## Incident Outcome

Status: Resolved

Root cause: HTTP was not permitted by the active firewalld public zone.

Recovery: Added the HTTP service to runtime and permanent configurations.

Validation: HTTP 200 OK from the Mac after firewall reload.

Note: This incident was simulated and resolved in an isolated homelab, not in a production environment.
