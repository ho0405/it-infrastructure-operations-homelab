# INC-0011 — Apache HTTP 403 Caused by SELinux File Context

## Lab Environment

- Platform: VMware Fusion on Apple Silicon
- Operating System: Rocky Linux 10.2 (ARM64 / aarch64)
- Hostname: dc-lab-rhel01
- Web Server: Apache HTTP Server 2.4.63
- Security: SELinux enforcing, targeted policy
- Incident Type: Application access failure
- Environment: Isolated infrastructure homelab

## Incident Summary

Apache was running, but an HTTP request returned 403 Forbidden after the SELinux context of the web application's index file was deliberately changed.

The incident simulated a common operational scenario in which a service is running but cannot access a required file because of a security policy.

## Expected Behaviour

Apache should serve /var/www/html/index.html and return:

HTTP/1.1 200 OK

The file's expected SELinux type was:

httpd_sys_content_t

## Incident Reproduction

Changed the file's SELinux type:

```bash
sudo chcon -t user_home_t /var/www/html/index.html
```

Tested the local application endpoint:

```bash
curl -I http://127.0.0.1/
```

Observed result:

HTTP/1.1 403 Forbidden

## Investigation

Inspected SELinux audit events:

```bash
sudo ausearch -m AVC,USER_AVC -ts recent -i
```

The audit log reported:

```text
avc: denied { read }
comm=httpd
name=index.html
scontext=system_u:system_r:httpd_t:s0
tcontext=unconfined_u:object_r:user_home_t:s0
tclass=file
permissive=0
```

The audit record also showed that the file operation failed with EACCES.

## Root Cause

Apache ran under the SELinux domain httpd_t.

The index file was incorrectly labelled user_home_t, which was not an appropriate content type for the web server.

SELinux enforcing mode prevented Apache from reading the file, resulting in HTTP 403.

The Apache service itself did not need to be restarted.

## Resolution

Restored the default SELinux file context:

```bash
sudo restorecon -v /var/www/html/index.html
```

The file type was restored to:

httpd_sys_content_t

Verified the application:

```bash
curl -I http://127.0.0.1/
```

Observed result:

HTTP/1.1 200 OK

## Operational Lessons

1. A running service does not guarantee application availability.
2. HTTP 403 may result from operating-system security policies rather than application-level authorization.
3. SELinux AVC audit records provide evidence of access denials.
4. Restore the correct file context instead of disabling SELinux.
5. Validate the application endpoint after applying a fix.

## Interview Summary

"In my Rocky Linux homelab, I simulated an Apache outage by assigning an incorrect SELinux file context. The service was running, but the application returned HTTP 403. I examined the SELinux AVC audit records, identified the denied file access, restored the correct context with restorecon, and verified HTTP 200 without disabling SELinux."

## Outcome

Status: Resolved

Validation: Apache returned HTTP 200 after SELinux context restoration.

Note: This was a controlled homelab incident, not a production outage.
